# Отчёт по фазе 7 «Эксплуатация»

Дата: 2026-07-31

Предыдущая попытка была прервана по лимиту ходов, оставив рабочую базу:
`ops/observability/` (Prometheus/Alertmanager/Grafana + подключение в
`docker-compose.yml`), `ops/backup/` (`pg_dump.sh`/`restore.sh`),
`ops/systemd/*`, `ops/retention/run.sh`, метрики
`services/sim-engine/src/metrics.ts` и
`services/reflection-worker/src/metrics.ts`, восстановление мира
`services/sim-engine/src/persistence/restore.ts`, полную интеграцию в
`docker-compose.yml`. Эта фаза не переписывала готовое — она (а) прогнала
весь гейт **живьём** на уже работающем боевом стеке (поднятом с фазы 6,
реальный трафик к Anthropic API) и (б) дописала недостающее: `ops/README.md`
(эксплуатационная документация, на которую уже ссылались юниты systemd) и
тест правил алёртов на синтетических данных. Живая проверка обнаружила и
исправила **три реальных дефекта**, невидимых при чтении кода — подробности
и обоснование каждого в `ops/DEVIATIONS.md` («2026-07-31 — фаза 7
«Эксплуатация»»).

## Что сделано

### Унаследовано из предыдущей попытки (проверено, не переписано)

- Экспорт метрик Prometheus: `services/sim-engine/src/metrics.ts` (:9464) —
  население, рождения/смерти по причинам, продолжительность жизни,
  ночные смерти от хищника, поведенческая дивергенция когорт,
  среднее/стандартное отклонение навыков, сигналы (поданные/опровергнутые),

  доля спящих по фазе суток, давление сна; `services/reflection-worker/src/
  metrics.ts` (:9465) — вызовы LLM по типу/модели/исходу, стоимость,
  латентность.
- Grafana-дашборд `ops/observability/grafana/dashboards/aurwin.json` (18
  панелей, покрывают все пункты 6.1 дословно) + автопровижининг датасорса и
  дашборда.
- Alertmanager + 5 правил алёртов `ops/observability/prometheus/alerts.yml`
  (остановка тика > 2 мин, обе видоспецифичные популяции, доля ошибок LLM >

- systemd-юниты `ops/systemd/aurwin-{sim-engine,reflection-worker,
  api-gateway}.service` (autostart, `WantedBy=multi-user.target`) +
  `aurwin-{backup,retention}.timer`.
- Восстановление мира при рестарте (`persistence/restore.ts` +
  `index.ts`): чтение `world_clock`/`creatures`/`bonds`/`aversions`,
  genesis не повторяется, тик — монотонный счётчик (правило «время после
  паузы не догоняется» соблюдено конструктивно: рестарт просто резюмирует
  `tick_` с сохранённого значения, никакой перемотки нет).
- `ops/backup/pg_dump.sh` (ежесуточно, ротация по `AURWIN_BACKUP_RETENTION_DAYS`)
  + `ops/backup/restore.sh` (интерактивное подтверждение, CLAUDE.md п.6) +
  WAL-архивация в `docker-compose.yml`.
- `ops/retention/run.sh` → `docker compose run --rm db-maintenance` →
  `runRetentionMaintenance()` (из фазы 2).

### Добавлено в этой фазе

- **`ops/README.md`** — эксплуатационная документация (уже требовалась
  `Documentation=file:///opt/aurwin/ops/README.md` во всех юнитах systemd
  из предыдущей попытки, но файла не было): как смотреть метрики/дашборд с
  таблицей URL/портов, обзор всех 5 алёртов и как проверить их без
  вмешательства в боевые данные, как перезапускать (systemd-путь и
  docker-compose-путь, включая поведение при разрыве связи с Postgres), как
  откатиться (два уровня — снапшот в БД vs pg_dump/WAL, с конкретными
  командами `restore.sh`), ретенция, секреты.
- **`ops/observability/prometheus/alerts_test.yml`** — `promtool test rules`
  на синтетических временных рядах, по одному срабатывающему и одному
  не-срабатывающему сценарию на каждое из 4 правил (тик, обе популяции, доля
  ошибок LLM, расход LLM). Нужен, потому что в боевом мире на момент фазы
  популяция органически ВЫШЕ порога (не ниже) — низкую границу без этого
  теста нечем было бы проверить, не убивая существ в боевой БД (запрещено
  CLAUDE.md п.6).

### Исправлено (реальные дефекты, обнаруженные живым прогоном)

1. **WAL-архивация Postgres падала на каждом сегменте** (`Permission
   denied`) — именованный volume `wal_archive` создаётся Docker с
   владельцем `root:root`, archiver-процесс Postgres работает от `uid
   postgres`. Исправлено: `command` сервиса `postgres` в
   `docker-compose.yml` теперь `chown postgres:postgres /wal-archive &&
   exec docker-entrypoint.sh postgres -c ...`.
2. **Разрыв простаивающего соединения с Postgres ронял весь процесс**
   `sim-engine`/`reflection-worker`/`api-gateway` необработанным
   исключением (`pg` `Pool` без слушателя `error`) — вместо штатной
   деградации получался незапланированный краш. Исправлено добавлением
   `pool.on("error", ...)` во всех четырёх `services/*/pool.ts`.
3. **`services/db/Dockerfile` не копировал `config/`** — любой плановый
   прогон ретенции падал бы `ENOENT` при чтении `constants.yaml` с первого
   дня эксплуатации. Исправлено добавлением `COPY config ./config`.

Также переписан устаревший комментарий в `reflection-worker/src/metrics.ts`
(ошибочно утверждал, что `index.ts` всё ещё заготовка фазы 1 — на самом
деле `recordLlmCall` уже вызывается из реального `worker.ts` фазы 6).

## Чем проверено (живой боевой стек, не только юнит-тесты)

1. **`npm test` → зелёный**: 29 файлов, 343 теста (без изменений в составе
   тестов — фаза не добавляла новых модулей симуляции, только
   инфраструктуру эксплуатации, которая проверяется живым прогоном ниже, а
   не мокнутыми юнит-тестами).
2. **`docker compose build && docker compose up -d`** — весь стек (9
   сервисов: postgres, sim-engine, reflection-worker, api-gateway,
   frontend, prometheus, alertmanager, grafana + `db-maintenance` по
   требованию) поднимается без ошибок с нуля.
3. **Гейт «рестарт → мир поднимается из снапшота и продолжает тикать»**:
   - `docker compose restart sim-engine` → лог `мир восстановлен из
     снапшота: тик 4485, 141 живых существ` (до рестарта — тик 4482), тик
     продолжил расти на следующих проверках (4485 → 4494 → 4499) без
     повторного genesis.
   - Дополнительно проверено на пересоздании контейнера Postgres
     (`docker compose restart postgres`, более жёсткий случай — обрыв
     живого соединения, а не просто рестарт sim-engine): после фикса №2
     `sim-engine`/`reflection-worker`/`api-gateway` остались живы,
     залогировали ошибку простаивающего соединения и самовосстановились
     без вмешательства, как только Postgres вернулся (тик продолжил расти:
     4552 → 4555 сразу после восстановления healthcheck).
4. **Гейт «алёрт срабатывает на искусственно заниженной популяции»**:
   `promtool test rules /tmp/alerts_test.yml` (скопирован из
   `ops/observability/prometheus/alerts_test.yml`) → `SUCCESS` по всем 4
   правилам (синтетические ряды, боевая БД не тронута). Дополнительно
   вживую подтверждено обратное направление того же алёрта на реальных
   данных: `AurwinPenguinPopulationOutOfRange` и
   `AurwinOrcaPopulationOutOfRange` оба реально `state: firing` в
   `http://127.0.0.1:9090/api/v1/alerts` прямо сейчас — боевая экосистема
   за время работы с фазы 6 органически выросла ЗА верхнюю границу (126-173
   пингвина при пороге 120, 15-20 касаток при пороге 12), что не является
   дефектом этой фазы (сама численность — не настраиваемый параметр,
   CLAUDE.md п.9), но полезный побочный сигнал для будущей балансировки
   ёмкости среды.
5. **Гейт «бэкап создаётся и восстанавливается»**: `ops/backup/pg_dump.sh`
   → новый дамп (348K) → `ops/backup/restore.sh <дамп> --yes` → сервисы
   остановлены, БД пересоздана, дамп восстановлен, сервисы подняты обратно
   → `sim-engine` восстановился из БД (`мир восстановлен из снапшота: тик
   4501, 150 живых существ`, тик до restore был 4503) и продолжил тикать
   (4505 сразу после) — без genesis, без потери населения.
6. **WAL-архивация**: после фикса №1 — пересоздание контейнера `postgres`
   → `/wal-archive` владеет `postgres:postgres` → `SELECT
   pg_switch_wal()` кладёт сегмент в архив без ошибок в логе. Проверено,
   что права переживают обычный `restart` (не только `recreate`).
7. **Ретенция**: `ops/retention/run.sh` после фикса №3 → успешно
   отработал на боевой БД (`decayed: 291` эпизодов), а не упал `ENOENT`.
8. **Метрики/дашборд/алёрты вживую**: `curl 127.0.0.1:9090/api/v1/targets`
   → оба job (`sim-engine`, `reflection-worker`) `up`; Grafana
   `/api/health` → `ok`, дашборд `aurwin-ops` виден через `/api/search`.
   Метрики LLM ненулевые и растут (`aurwin_llm_calls_total` — 38+ успешных
   вызовов, `aurwin_llm_cost_usd_total` — реальная накопленная стоимость) —
   подтверждает требование задания фазы: метрики опираются на реальный
   `reflection-worker` (фаза 6), не на заготовку.

## Что не сделано (сознательно)

- Внешний канал уведомлений для Alertmanager (Slack/email/webhook) — не в
  скоупе фазы 7 (нет креденшелов внешних сервисов в этой среде), алёрты
  видимы и проверяемы через UI/API Prometheus/Alertmanager, чего достаточно
  для гейта. Добавление receiver'а — правка одной секции
  `alertmanager.yml`, не требует изменения правил.
- Персистентный (переживающий рестарт воркера) бэкофф ретраев
  reflection-worker — уже зафиксировано как открытый пункт в фазе 6
  (`DEVIATIONS.md`, п.10), не расширялось в этой фазе (не часть задания
  «Эксплуатация», это внутренняя логика reflection-worker).
- Автоматический failover/HA Postgres (репликация, standby) — вне MVP
  (А.7 описывает один VPS, WAL-архивация — только PITR-подстраховка между
  дампами, не горячая репликация).
- Балансировка ёмкости среды в ответ на органически возросшую популяцию
  (респавн рыбы / летальность охоты, CLAUDE.md п.9) — не задача фазы 7
  («Эксплуатация» строит наблюдаемость и инфраструктуру, а не крутит
  параметры баланса); зафиксировано выше как наблюдение для будущей
  итерации балансировки (раздел 9 ТЗ).

Полное обоснование каждого исправления и решения — `ops/DEVIATIONS.md`,
раздел «2026-07-31 — фаза 7 «Эксплуатация»».
